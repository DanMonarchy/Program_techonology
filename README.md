# Вопросы для подготовки к сдаче

## Теория ООП

**1. Чем абстрактный класс отличается от обычного?**
Объект абстрактного класса создать нельзя (`new Beverage(...)` не скомпилируется). Он служит основой для наследников и может содержать абстрактные методы, то есть методы без тела, которые наследники обязаны реализовать. Обычный класс можно создавать напрямую, и все его методы имеют тело.

**2. Что такое полиморфизм и как он проявляется в цикле `foreach`?**
Полиморфизм означает, что один и тот же код работает с разными типами объектов, а каждый объект ведёт себя по-своему. В `foreach (Beverage drink in menu)` переменная имеет тип `Beverage`, но `drink.Serve()` и `ToString()` выполняют версию того класса, к которому объект относится на самом деле (`Coffee`, `Juice` и т. д.). Версия выбирается во время выполнения.

**3. Зачем нужен `override`?**
Он говорит компилятору, что метод наследника заменяет метод базового класса (абстрактный или виртуальный). Благодаря этому при вызове через базовый тип выполняется реализация наследника.

**4. Что произойдёт, если в наследнике не переопределить абстрактный метод?**
Код не скомпилируется: компилятор выдаст ошибку, что класс не реализует унаследованный абстрактный член (например, `Beverage.Serve()`). Исключение: если сам наследник тоже объявлен `abstract`.

## Интерфейсы

**5. Чем интерфейс отличается от абстрактного класса?**
Интерфейс описывает только контракт: что объект умеет делать (`IWarmable { void Warm(); }`). У него нет полей и конструкторов. Класс может реализовать много интерфейсов, но наследовать только один класс. Абстрактный класс может хранить состояние (поля, свойства), иметь конструкторы и готовые методы, и описывает, чем объект является.

**6. Почему интерфейс реализуют не все наследники, а только часть?**
Интерфейс реализуют только там, где это имеет смысл. Кофе можно подогреть, и `Coffee` реализует `IWarmable`. Сок подогревать не принято, поэтому `Juice` интерфейс не реализует, и ему не нужен метод `Warm()`, который ничего не делает.

**7. Что вернёт `t is IInterface`, если `t` не реализует интерфейс?**
`false`.

**8. В чём разница между `is` и `as`?**
- `is` проверяет тип и возвращает `bool`. В форме `drink is IWarmable warmable` при успехе сразу создаёт переменную нужного типа (pattern matching).
- `as` пытается привести объект к типу и возвращает сам объект или `null`, если приведение невозможно. Исключения при этом нет.

```csharp
if (drink is IWarmable warmable) { warmable.Warm(); }

IWarmable? w = drink as IWarmable;
if (w != null) { w.Warm(); }
```

## Инкапсуляция

**9. Зачем делать поля приватными?**
Чтобы внешний код не мог изменить внутреннее состояние объекта в обход правил класса. Доступ даётся через свойства и методы, и внутреннее устройство можно менять, не ломая остальную программу.

**10. Как приватное поле может использоваться в вычисляемом свойстве?**
Вычисляемое свойство находится внутри того же класса, поэтому оно видит приватные поля и может отдавать их значение наружу только для чтения:

```csharp
private readonly int _id;
public int Id => _id;
```

## Свойства

**11. Чем автосвойство отличается от обычного свойства с полем?**
У автосвойства (`public string Name { get; set; }`) скрытое поле создаёт компилятор, а логики в `get` и `set` нет. У обычного свойства поле объявляется вручную, и в `get`/`set` можно добавить проверки или преобразования.

**12. Что такое вычисляемое свойство? Почему у него нет backing-поля?**
Это свойство только для чтения, значение которого вычисляется из других данных при каждом обращении: `VolumeInLiters => Volume / 1000.0`. Своего значения оно не хранит, поэтому поле для него не нужно.

**13. В чём разница между `SpeedInMetersPerSecond => Speed / 3.6` и методом `GetSpeedInMetersPerSecond()`?**
Результат одинаковый, различие в смысле и записи. Свойство читается как данные (`obj.Prop`, без скобок), не принимает параметров и обычно работает быстро и без побочных эффектов. Метод подходит для действий, вычислений с параметрами или тяжёлых операций.

## Конструкторы

**14. Зачем перегружать конструкторы?**
Чтобы объект можно было создавать разными удобными способами: `new Coffee(1, "Latte", 300, true)` с полным набором данных или короче, только с названием.

**15. Что делает `: this(...)` в объявлении конструктора?**
Вызывает другой конструктор этого же класса до выполнения своего тела. Так не приходится дублировать код: `Beverage(string name) : this(0, name, 0)` передаёт значения по умолчанию в основной конструктор.

**16. Можно ли вызвать `base(...)` и `this(...)` в одном конструкторе?**
Нет. У конструктора может быть только один инициализатор: либо `base(...)`, либо `this(...)`. Но цепочка допустима: конструктор с `this(...)` вызывает другой конструктор того же класса, а уже тот вызывает `base(...)`.

## Перечисления

**17. Зачем использовать `enum` вместо строк или чисел?**
`enum` ограничивает набор допустимых значений, защищает от опечаток (`"Hott"`), делает код читаемым (`DrinkTemperature.Hot` вместо `0`) и подсказывается средой разработки.

**18. Как объявить `enum` в отдельном файле?**
Создать файл с именем типа (`DrinkTemperature.cs`):

```csharp
public enum DrinkTemperature
{
    Hot,
    Cold,
    Room
}
```

**19. Какое значение по умолчанию получает `enum`-свойство без явной инициализации?**
Значение `0`, то есть первый элемент перечисления, если ему не заданы другие числа. Для `DrinkTemperature` это `Hot`.

**20. Как задать значение по умолчанию для автосвойства типа `enum`?**
Через инициализатор автосвойства:

```csharp
public DrinkTemperature Temperature { get; set; } = DrinkTemperature.Hot;
```

**21. Что произойдёт, если присвоить `enum`-свойству число, не входящее в список значений?**
Просто так число присвоить нельзя, нужно явное приведение: `(DrinkTemperature)5`. Тогда ошибки не будет ни при компиляции, ни при выполнении: значение сохранится, но имени у него нет, и при выводе напечатается `5`. Поэтому числа вне списка лучше не присваивать.

## Git

**22. Зачем создавать отдельную ветку для домашнего задания?**
Ветка `main` остаётся чистой (в ней только стартовый шаблон), работа ведётся изолированно, изменения удобно проверять и при необходимости откатывать.

**23. Что такое осмысленное сообщение коммита?**
Короткое описание того, что именно сделано в этом коммите, по которому понятно содержание изменений без просмотра кода. Например: `Subtask #15: реализованы наследники, интерфейс и ToString`. Сообщения вроде «fix» или «правки» осмысленными не считаются.

**24. Как связать коммит с номером подзадачи в трекере?**
Указать номер задачи в виде `#<номер>` в тексте сообщения коммита. GitHub превратит его в ссылку и покажет коммит внутри соответствующей задачи.

**25. Что произойдёт, если сделать все три подзадачи одним коммитом?**
История потеряет структуру: не видно, как шла работа, а в трекере нельзя привязать результат к каждой подзадаче отдельно. Задание требует отдельный коммит на каждую подзадачу, так что это будет считаться ошибкой оформления. Кроме того, неудачную часть сложнее откатить.
